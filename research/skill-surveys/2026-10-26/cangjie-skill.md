## 2. 它是什么

仓颉把书、长视频、播客、课程或访谈蒸馏成一组可供代理调用的技能，对象是材料里的方法，不是作者本人。仓库自己的定位写明：女娲蒸馏人，仓颉蒸馏书，另有配套机制用于技能后续迭代。本笔记只谈仓颉，不展开配套仓库。

方法名是 RIA-TV++。SKILL.md 将其写成固定流水线：先整书理解，再并行提取，用三重验证筛知识，再用晋级门决定谁成为独立技能，然后做成能力卡、做卡片之间的链接、做压力测试，最后编译交付。

## 3. 写法特点

- description 用使用人的原话作触发（拆书、把某书做成技能、处理视频或播客稿），并指向这是元技能：产物是别的技能，不是对这本书的读后感。
- 阶段写在 `SKILL.md`，每阶段指向 `methodology/` 里的一篇。总览文件声明自己解释为何这样设计，执行时以 SKILL.md 和分阶段文件为准，避免两处都写操作细节。
- 阶段 1.6 的晋级门把「知识上成立」和「值得单独成一个技能」分开。未晋级的内容不删除，留在来源入口里当能力卡。独立技能要有清楚的触发条件，并和入口之间有相近的反例，减少叫错。
- 能力卡要求能执行、有边界。质量红线包括：验证不通过不输出、引用长度受控、每条能力只有一个去向、编译产物要经过仓库内校验脚本、本地改过的生成目录不能被静默覆盖。缺了重要部分只能交标出范围的草稿，不能宣称完整通过。
- 压力测试要求晋级技能和留在路由里的技能都真正做完代表任务并核对输出。只证明「会被调用」不算通过。
- 输出由脚本从中间产物编译。查阅时，可发现入口有软预算，默认 8 个（含 1 个来源路由入口），避免一本书拆出一长串技能把宿主检索挤满。

## 4. 原理与设计意图

`methodology/00-overview.md` 写明：给人读的笔记强调故事和金句，给代理用的技能强调触发、步骤和停止条件。调用错了，技能要么永不出现，要么不该出现时出现。所以流水线后半段都在处理触发和验收，而不是继续摘要。

晋级门是为了控制技能数量。每条知识点都做成顶层技能，description 会互相遮盖。留在一个来源入口里，由入口再路由，和「一个目录一个职责」更一致。

三重验证来自和女娲类似的想法：只出现一次的说法，不足以做成稳定规则。压力测试则把「写得出卡片」和「拿卡片能做完一件事」分开，与本库「单测通过不等于 LIVE」是同一类区分。

## 5. 对照本库

本库不从书籍生产技能。仓颉对本库的用处是技能粒度：什么应该独立成 `skills/<name>/`，什么应该留在某个技能的 `references/`。

### 可借鉴

- 站点继续留在 `drission-crawler/references/sites/<代号>/`，由总技能路由。只有当触发条件已经互相干扰（例如一段 description 同时命中两套互斥流程）时，才考虑新的顶层技能。这与晋级门「知识成立仍可留在入口内」一致。
- `demo-kickoff-card` 与完整需求收集卡的关系可以维持现状：开工卡是 DEMO 用的短表，完整交接仍用八节卡。不把四块再拆成四个技能。
- description 里的反例继续写。仓颉要求独立技能和入口之间有近邻负例。本库 `evals.json` 里「不该触发」的样本承担同一职责，例如论文版式不走 `work-doc-writer`，营销页不走 `government-service-design`。
- 材料不足时交付标出范围的草稿。开工卡用「待确认」，收工用「未验收完成」。不要在缺 LIVE 时把结论写成已完成。

### 不要照搬

- 不把拆书、视频蒸馏、能力卡编译器加入本仓库。没有相应交付任务，也没有 Bundle 和编译脚本的维护责任。
- 不把 RIA 读书法的栏目写进 `work-doc-writer`。工作文档对照程序源码和界面原文，不对照书籍章节。
- 不把「一本书一组技能」用于招标、OCR、发票或比对归档。这些是同一交付链路里的不同站点或单据，优先用站点包和模板，而不是一组新技能名。
- 不把仓颉的自动迭代接口写进 `dev-process-handoff`。交接仍是变更摘要、依据和完成标准，供人接手，不是喂给另一个进化技能。

## 6. 一句话建议

用晋级门检查技能要不要新开目录；本库维持「一个交付场景一个技能，细节放引用」，不引入拆书流水线。
